# Solution Document — WMSNow Redwood Mobile

**Date:** 2026-07-09 through 2026-07-10
**Prepared by:** Claude Code, working session with the project owner

---

## 1. Context

Oracle Custom App's core challenge is that Oracle's Redwood Mobile RF API (`get_next_rwmobile_page`) is not publicly documented in enough detail to build against directly — every request/response shape, every control-key value, and the exact session-conflict behavior had to be reverse-engineered from live captures (Postman, the app's own on-device debug sheet, and direct live testing against a real customer WMS instance). This document summarizes the issues found and resolved across this engagement, the evidence behind each fix, and the current state of the application.

**Project split (2026-07-10):** the codebase forked into two folders — `redwood_v2` (frozen, already-demonstrated POC; §2.1-§2.11 below all happened here and it is not modified further) and `wmsnow_redwood_v3` (active development line; §2.12 onward happened here). See §2.12 for the fork mechanics.

## 2. Problems Addressed

Six distinct, real issues were identified and fixed early in this engagement, in `v2` (§2.1-§2.6). Three earlier ChatGPT-authored reviews of the session-management design were also investigated and answered (see §2.1) before the live issues below surfaced. Later the same day, a new multi-field TAB navigation feature was built and live-verified end-to-end in `v2`, surfacing four further issues during rollout (§2.8-§2.11), documented in §2.7. The following day, the project split into `v2`/`v3` (§2.12), and five further enhancements were built in `v3` (§2.13-§2.17).

### 2.1 Session-management design review (three rounds)
A series of external reviews questioned whether the app's session-identity handling matched the intended Oracle RF model. Investigation (reading the code, then live-testing against Oracle directly) found:
- The app's frozen-forever session model at the time was internally consistent and matched a subset of live-tested behavior, but a stale code comment (claiming identifiers "rotate on nearly every call" and must always be the latest) was actively contradicting the code and was the direct cause of the reviews' confusion.
- A claimed "Postman-validated" basis for the frozen model was, on inspection, a description of the developer's own earlier testing, not something independently re-verified — this was disclosed honestly rather than re-asserted as settled fact.
- Live curl testing against the real Oracle instance (see §4) was used to test the frozen-vs-latest question directly, which ultimately led to reversing the model entirely (§2.2).

### 2.2 Session identity model: frozen → track latest
**Symptom:** intermittent "this user session has expired" errors, and unpredictable behavior recovering from the "another active session" conflict.
**Root cause:** the app pinned `clientid`/`htmlrfid` to the very first response of the session and never updated them, on the theory that Oracle's differing echoed values across a session were not meaningful. Extensive live testing on 2026-07-09 — including the developer's own step-by-step Postman testing, cross-checked against independent curl testing here — repeatedly showed that once a session conflict is resolved, continuing to use the *original* pre-conflict identity produces "session expired," while adopting whatever identity the most recent response carries does not.
**Fix:** `_captureSession()` now updates `clientid`/`htmlrfid` from every response, with no freezing (`lib/main.dart`).

### 2.3 "Another active session" conflict: made fully silent and more robust
**Symptom:** operators occasionally saw a Yes/No confirmation dialog, and in some cases the app gave up with a "session conflict did not clear" error after a single failed attempt.
**Root cause:** two separate issues layered together — (a) the app was designed to show this dialog interactively for the very first occurrence per session, when live testing (and the developer's own reference documentation for this API) showed it should always be answered automatically, with no user decision involved; and (b) the automatic "yes" retry was originally bounded to a single attempt, but live testing showed clearing this conflict can legitimately take 2-3 (occasionally more) consecutive attempts, unpredictably, even on a completely fresh, never-before-used account.
**Fix:** the dialog is never shown to the operator now, for any occurrence. The retry bound was widened (1 → 3 → 6 attempts, with a short pacing delay between retries) based on directly observed live behavior.
**Investigated and ruled out as contributing causes** (each tested live against the real instance before being ruled out, rather than assumed): the `env_name` request field's value, presence/absence of `clientid` on the yes/no answer, which specific `htmlrfid` is used to answer "yes" (the original login one vs. the conflict response's own), answering with `X` instead of `A`, and the Oracle load-balancer sticky-route cookie. None of these changed the pattern — the conflict is best understood as routine, occasionally-flaky Oracle-side behavior on this environment, not a client request-shape defect.

### 2.4 Facility Code / Company Code submission doing nothing on Submit
**Symptom:** entering a facility code or company code and tapping Submit produced no visible effect — the screen just sat there.
**Root cause:** these submissions used a dedicated `facility_code` field with `keyboard_input` left empty. Live testing (the developer's own fresh Postman session, cross-checked live) showed the server only reads `keyboard_input` for entry-dialog submissions of any kind — the dedicated field was silently ignored, so the server received an effectively empty submission.
**Fix:** removed the dedicated `sendFacilityCode()` method entirely; all entry-dialog submissions (facility code, company code, LPN, everything) now go through the same generic `sendInput()` call, `{htmlrfid, env_name: <instance>, keyboard_input: <value>}`, with `env_name` set to the actual instance name rather than empty.

### 2.5 Restrict Company (and similar screens) rendering as blank, unlabeled boxes
**Symptom:** the Restrict Company screen showed a handful of empty text boxes instead of the expected list of company names.
**Root cause:** the generic screen renderer (`_ScreenView`) only knew how to render `page_content` items of `type: "entry"` as text fields — it rendered every item indiscriminately as a text field, regardless of type, so the screen's `label` item ("Restrict Company:") and its 29 `button` items (FLOW, IKEA, MARINA, ...) were each rendered as a blank, unlabeled text box.
**Fix:** `_ScreenView` now branches on each item's `type`: `label` renders as plain text, `button` renders as a tappable card that submits its index immediately on tap, and `entry` keeps its existing text-field-plus-Next-button behavior (now only shown when at least one entry field is actually present on the screen).

### 2.6 Back button not returning to the previous screen
**Symptom:** on some screens (e.g. "Rcv ASN Units"), pressing the app's back arrow had no visible effect.
**Root cause:** the back arrow (and the Cancel/OK actions on entry/info dialogs) were hardcoded to always send `action_keys: "W"`. Comparing the app's own debug-sheet capture of that exact screen's response showed its `ctrl_keys` array labels `F2`, not `W`, as "Previous Screen" — the server was silently ignoring the invalid `W` and re-displaying the same screen, which looked exactly like "back doesn't work."
**Fix:** back/Cancel/OK now look up whichever `ctrl_keys` entry on the *current* screen has a value containing "Previous Screen" and send that key, falling back to `W` only if the current screen defines no such entry.

### 2.7 New feature: multi-field sequential (TAB) navigation for transactional screens
The customer specified a new capability matching real RF terminal behavior: transactional screens (e.g. a Receiving screen) present several fields that must be filled **one at a time, in strict server-tracked order**, not as a free-form form. This was designed, then live-verified end-to-end on 2026-07-09 using a real transaction on a customer test instance (Dock=D22, LPN, Item, Qty, Batch, Expiry Date, ending the LPN with Ctrl-E), with every step cross-checked against the customer's own parallel Postman testing before being implemented in code. Key facts established live and now built into `_ScreenView`:
- The server tracks a single "current" field per screen (`focus: true` in the response) — only that field is genuinely editable; every other field is shown read-only.
- Submitting a real value via `keyboard_input` (now requiring `clientid` on this class of screen — see §2.3's investigation, this was the missing piece for these specific screens) auto-advances the server's cursor on its own and can auto-populate other fields as a side effect (e.g. submitting Dock auto-filled Shipment and Shpmt Type).
- A distinct request shape moves the cursor with no value: `{clientid, htmlrfid, env_name, action_key: "TAB"}` (note `action_key`, singular — every other action-key call in the app uses `action_keys`, plural).
- A field carrying an auto-populated but not-yet-confirmed value cannot simply be skipped with TAB — it must be explicitly (re-)submitted first, or the server returns `dialog_message: "Required Field"`.
**Implementation:** each entry field got its own small TAB icon-button (enabled only when that field is current) that submits the typed value if present, else sends the bare TAB action; a "focus"-driven current-field tracker in `_ScreenViewState` drives which field is editable and which are read-only, per the requirement in the developer's written specification for this feature.

### 2.8 TAB button discarding typed text, with no visible cursor
**Symptom:** entering "D22" in the Dock field and tapping TAB caused the typed value to disappear, and it was unclear which field was now active.
**Root cause:** the TAB button unconditionally sent the bare no-value TAB request regardless of what had been typed, discarding it; separately, Flutter's `autofocus` only fires once per widget lifetime, but the same `_ScreenViewState` persists across an entire multi-step transaction, so no field after the very first ever received visible focus.
**Fix:** the TAB button is now "smart" — it submits the current field's typed value if non-empty (which the server then auto-advances past on its own) and only sends the bare TAB action if the field was left empty. A dedicated `FocusNode` per field plus a post-frame callback that explicitly requests focus whenever the current field changes now keeps the cursor visibly and correctly positioned.

### 2.9 Auto-populated Shipment field displaying empty
**Symptom:** after submitting Dock, the response showed Shipment auto-filled with a real value server-side, but the app's Shipment field appeared blank.
**Root cause:** the per-field resync logic deliberately skipped resyncing whichever field was "current," to avoid clobbering text the operator was actively typing — but this treated "is current" as synonymous with "user is actively typing in it," which is wrong for a field that becomes current AND gets auto-populated in the very same response (nothing was ever typed there to protect).
**Fix:** the resync logic now specifically tracks whether a field *just became* current in this response (as opposed to having already been current) and resyncs its displayed text in that one case, while still protecting genuinely-in-progress typing on a field that was already current before this response.

### 2.10 Batch Nbr text carrying over into the Expiry Date prompt
**Symptom:** after entering a Batch Nbr and pressing TAB, the next prompt (Expiry Date) showed the just-entered batch number pre-filled in its box.
**Root cause:** the shared entry-dialog widget (`_EntryView`, used for both `entry` and `barcode` dialog types) had no Flutter widget `key`. Two consecutive but structurally-identical prompts in the same tree position caused Flutter to reuse the exact same State object and its `TextEditingController`, carrying the old text forward into the new prompt.
**Fix:** gave `_EntryView` an explicit `key: ValueKey('$_renderCount-$_htmlrfid')`, where `_renderCount` is a new monotonic counter incremented on every response — forcing Flutter to create a fresh State (and thus a fresh, empty controller) for every new prompt, even ones that look identical in structure.

### 2.11 "Ctrl-E: End LPN" missing from the Actions menu, and error dialogs not dismissing
**Symptom (End LPN):** partway through a Receiving transaction, the "End LPN" action visible in an early screenshot was no longer offered.
**Root cause (End LPN):** not a data or server-side issue — `ctrl_keys` had never been wired up for `_ScreenView` at all; the control-key Actions menu only ever existed inside `_MenuView` (the main menu), so generic transactional screens had no UI path to their own control keys, regardless of what the server offered.
**Fix (End LPN):** moved the Actions menu into the shared `Scaffold`/`AppBar`, so every screen type — main menu, entry dialogs, and generic transactional screens alike — reads `ctrl_keys` from its own current response and exposes them uniformly.
**Symptom (dismiss):** entering a badly-formatted date produced an "Invalid format" error, but tapping OK/back did nothing — the same error just stayed on screen.
**Root cause (dismiss):** the same class of bug as End LPN, found immediately after fixing it — error/info dialogs typically carry no `ctrl_keys` of their own, and the "Previous Screen" key lookup (§2.6) recomputed fresh from every response, falling back to a hardcoded `W` when the current response had none. On a screen whose real key was `F2`, this silently sent the wrong key; confirmed via the on-device debug sheet showing byte-for-byte the same `htmlrfid` and response before and after tapping OK.
**Fix (dismiss):** the last known-good "Previous Screen" key is now persisted across responses and only overwritten when a response actually supplies a fresh match, rather than being reset on every build.

### 2.12 Project split: `redwood_v2` (POC) → `wmsnow_redwood_v3` (active development)
At the developer's request (2026-07-10), the codebase was forked so the demonstrated/tested POC (`v2`) stays untouched as a reference while all further customization work happens in a separate `v3` folder.
- **Mechanics:** `v3` was created as a full folder copy of `v2` (robocopy, same exclusions used for the dated backups: `build`, `.dart_tool`, `.gradle`, `.idea`, `android\.gradle`), then re-identified as its own distinct app so both can be installed on the same test device simultaneously: Android `applicationId`/Kotlin package (`MainActivity.kt` moved to a new package directory); Android app label; `MaterialApp.title`; matching renames across the Windows (`CMakeLists.txt`, `Runner.rc`, `main.cpp`), web (`manifest.json`, `index.html`), and iOS/macOS/Linux boilerplate, plus `test/widget_test.dart`'s import.
- **Rebrand (2026-07-23):** the client is moving forward under the "WMSNow" name, so every identifier and visible string from the original fork was retired app-wide. Same structural-rename mechanics as above: pubspec `name` → `wmsnow_redwood_v3`; Android `applicationId`/Kotlin package → `com.example.wmsnow_redwood_v3`; iOS/macOS bundle IDs → `com.example.wmsnowRedwoodV3`; Windows/Linux binary + application IDs → `wmsnow_redwood_v3`; visible app title/login heading → "WMSNow WMS Mobile"; app icon set from the official "WMS Mobile" logo (the circular "W" mark on a white background, cropped from the supplied lockup) via `flutter_launcher_icons` across Android/iOS/macOS/web/Windows. Applied to a fresh copy of the folder at `C:\dev\wmsnow_redwood_v3` (the prior folder is being retired once the new copy is confirmed working). The seed WMS environment entries in `app_config.dart` were deliberately left untouched at the time — they're real, user-editable Oracle instance connections, unrelated to app branding (they were later removed entirely, 2026-09-28, so no customer's environment name ships as a default in shared source).
- **Verified live**: both `com.example.redwood_v2` and `com.example.wmsnow_redwood_v3` confirmed installed side-by-side on the Nokia C01 Plus test device, each launching independently.
- `docs/*.md` were copied as-is into `v3` at fork time and described only `v2`'s history until the 2026-07-10 update — a known, expected gap between the fork and that document refresh, not a bug.

### 2.13 New feature: scan and calendar-date helpers on every entry field
The developer asked for a scanner icon on every text field and a calendar icon on every date field, so operators can scan or pick a date instead of typing.
- **Scanning**: `mobile_scanner` (already a pubspec dependency, unused until now) is wired into a reusable `_scanBarcode(context)` helper — a full-screen camera view that pops with the first decoded barcode's raw value. Added to both `_EntryView` (single-field dialogs) and each entry row in `_ScreenView` (multi-field screens), gated the same way the existing submit/TAB buttons already are (hidden on `masked` fields in `_EntryView`; shown only on the current, non-readonly field in `_ScreenView`).
- **Date picking**: a `_pickDate(context, controller)` helper opens a standard Flutter date picker and writes the result back as `MM/DD/YYYY` — matching the format already confirmed live for Expiry Date entries. Shown wherever a field's label/prompt text contains "date," case-insensitively (the RF API has no dedicated date field type to key off).
- Required adding the `CAMERA` Android permission (previously absent, since the dependency had never actually been exercised).
- **Live-verified** on-device: the scan icon opens the camera view and Android's runtime camera-permission prompt appears correctly on a real Receiving screen's Dock field.

### 2.14 Truck Temp field appearing on every LPN screen, not just Receiving
**Symptom:** the Truck Temp field showed up on essentially every screen with an LPN field — Split IBLPN, Manual Locate LPN, RF Lock/Unlock IBLPN, etc. — not just the intended receiving transaction.
**Root cause:** the injection rule only ever checked whether a field's label contained `"lpn"` — true of most of the RF menu, since "LPN" is one of the most common field labels in this WMS.
**Fix:** `_RuntimeScreenState` now tracks `_currentTransactionName`, the name of whichever mainmenu item was tapped to reach the current screen (captured in `_MenuView`'s tap callback, held for the whole transaction including through End LPN's loop-back to the top of the screen). The Truck Temp injection now additionally requires this name to contain the customer's real transaction name (baked in per build, not hardcoded — see `AppConfig.truckTempPageTitleMatch`) before the label-based check applies.

### 2.15 Truck Temp field/lookup correction: `cust_decimal_1`, and facility/company scoping
Following the developer's own reference for how Truck Temp should actually be persisted:
- **Field corrected**: the target field is `cust_decimal_1` (a decimal-typed custom field), not `cust_field_1` (a generic text field guessed early in the engagement before the exact field was confirmed).
- **Lookup scoped by facility and company, not shipment_nbr alone**: `RwmobileService.findEntity()` was generalized to accept multiple ANDed query filters instead of just one. The shipment lookup now filters by `shipment_nbr` **and** `facility_id__code` **and** `company_id__code` — live-tested that shipment_nbr alone isn't guaranteed unique across facility/company. The facility/company codes are read directly off `content.headers.fac_code`/`comp_code`, present on every RF response, rather than tracked from whatever the operator previously typed into a Change Facility/Restrict Company dialog (which would have been far more fragile).
- **PATCH shape re-confirmed live**: the developer's own reference showed the GET and PATCH using an identical query-filtered URL; live-tested against the real instance and found the query-filtered PATCH returns `405 METHOD_NOT_ALLOWED` — the existing GET-then-PATCH-by-`/id/` pattern (already working from earlier in the engagement) was correct and is unchanged, only the GET's filters and the target field were updated.
- **Auto-lock when already recorded**: the shipment lookup now fires as soon as the Shipment field is confirmed (not deferred to save time), and if `cust_decimal_1` already has a value, the Truck Temp field displays it read-only instead of an empty editable box — the operator can't accidentally re-enter or overwrite an already-recorded reading.

### 2.16 Truck Temp save timing: deferred to End LPN
**Symptom (developer-flagged, not yet visibly broken):** the PATCH was firing the moment the LPN field was submitted — i.e. at the *start* of that LPN's line entries, before Item/Qty/Batch/Expiry Date were even entered — rather than when the operator actually finished with that LPN.
**Root cause:** the original design tied the save to the same field submission that triggered the injected field's own display, since that was the simplest available hook at the time it was first built.
**Fix:** submitting the LPN field now only captures the typed Truck Temp value (`_pendingTruckTemp`), without saving it. The actual PATCH fires from the Actions menu's `onSelected` handler, specifically when the pressed key matches whichever `ctrl_keys` entry means "End LPN" on the current screen (looked up dynamically, the same pattern already used for "Previous Screen" — not assumed to always be the letter `E`). If the field was locked (already had a recorded value), there's nothing pending to save, so End LPN doesn't trigger a redundant PATCH.

### 2.17 New feature: Split IBLPN photo capture
The developer asked for a camera capture step on the Split IBLPN screen, between the Move Qty and Move to LPN fields — captured any time on the screen, but only actually saved to local storage when Move to LPN is submitted.
- **Implementation**: `image_picker` (new dependency) launches the native camera app for a one-off photo; the picked file is held in state until the Move to LPN field is submitted, at which point it's copied into the app's own local documents storage (`path_provider`, new dependency) under a `captured_images` folder, named after the LPN value and a timestamp.
- **Bug found via live debug-sheet capture**: the camera button initially failed to appear at all. Two root causes, found in sequence:
  1. The injection was first scoped by `_currentTransactionName` containing "split iblpn" (mirroring Truck Temp's pattern) — live testing showed the real mainmenu button's text couldn't be assumed to literally contain that substring, silently hiding the button. Fixed by dropping the transaction-name scoping for this feature entirely, relying on the field match alone (see next point) — "move to lpn" (or the tag, below) is specific enough on its own not to need it.
  2. Even after that fix, the button still didn't appear. The developer shared the on-device debug sheet's raw JSON for the actual Split IBLPN screen, which showed "Move to LPN: " is a separate `type: "label"` page_content item — the entry field that follows it has `label: ""` (blank), with a distinct technical `tag: "to-lpn"`. The injection had been matching on label text, which was empty for this exact field; switched to matching on `tag` instead, which fixed it immediately.
- **Verified live end-to-end**: captured a photo on the real device, confirmed it landed in the app's private storage (`app_flutter/captured_images/`) via `adb shell run-as`, and pulled a copy to the PC to visually confirm it was a valid, uncorrupted image. Per the developer's explicit decision, no automatic sync/export off the device was built — the photo stays local to the app only.

## 3. Key Technical Decisions & Rationale

| Decision | Rationale |
|---|---|
| Session identity tracks latest, not frozen | Reversed after extensive live evidence (§2.2); the frozen model is now known to fail once a session conflict transitions identity server-side. |
| Session conflicts resolved 100% silently, always | Matches the developer's own reference documentation for this API, and live testing confirmed it's routine expected behavior, not something requiring operator judgment. |
| Retry bound widened but still finite (6, not unbounded) | An earlier ~300-attempt unbounded drain loop was suspected of manufacturing its own runaway conflict rather than draining a real backlog; a small, generous-but-bounded retry avoids both extremes. |
| No dedicated request shape per business field (facility code, company code, etc.) | Everything the operator types into an entry dialog uses the same generic `keyboard_input` shape — confirmed live, and consistent with the principle that the client should never special-case business content. |
| Screen rendering fully driven by each item's own `type` | Oracle can return `label`/`button`/`entry` items in any combination on any screen; hardcoding an assumption that a screen is "all entry fields" breaks the moment a screen isn't (as it did here). |
| "Previous Screen" key resolved dynamically per screen | Confirmed live that this key is not constant across all screens - the same principle already applied to menu buttons/control keys had not yet been applied to this one specific action. |
| Multi-field cursor tracked from the server's own `focus` flag, not client-side assumption | Matches how a real RF terminal behaves (single active field), and avoids the client guessing which field is "next" when the server can auto-populate and re-target focus as a side effect of a submission. |
| Every entry field gets its own TAB button rather than one shared "Next" button | The developer's explicit requirement, and the only way to submit or skip an arbitrary field once fields become individually current/read-only rather than a single flat form. |
| Widget `key`s added wherever consecutive different prompts can occupy the same tree position | Flutter reuses State (and controllers/focus) across structurally-identical rebuilds unless a distinguishing `key` forces a fresh instance - this was the root cause of two separate bugs (§2.10, and the "Previous Screen" fallback pattern in §2.11) and is now understood as one general class of pitfall, not two unrelated ones. |
| `v2`/`v3` split via plain folder copy + app re-identification, not git | No version control was in use; a folder copy matches the existing dated-backup convention and lets both builds run side-by-side on the same test device for direct comparison. |
| Truck Temp injection scoped by `_currentTransactionName` (which mainmenu item was tapped), not label text alone | "lpn" alone matches most of the RF menu (§2.14); the mainmenu item name is the only reliable signal for "which transaction is this" the API provides. |
| Split IBLPN photo capture matched on field `tag`, NOT label text or transaction name | Live testing showed both alternatives were fragile here specifically: the visible "Move to LPN" caption and its input box are separate page_content items with the entry's own label blank (§2.17), and the mainmenu button's real text couldn't be assumed to contain "split iblpn." `tag` is a stable technical identifier and didn't share either problem. |
| Truck Temp shipment lookup scoped by facility_id__code/company_id__code (sourced from response headers), not shipment_nbr alone | Live-confirmed shipment_nbr isn't guaranteed unique across facility/company; the codes are already present on every response, so no extra tracking or operator input is needed to get them. |
| Truck Temp PATCH stays `/entity/ib_shipment/{id}/`, not a query-filtered collection URL | Live-tested 2026-07-10 that the query-filtered shape (matching the GET) returns 405 on this API - confirmed empirically rather than assumed from the developer's reference alone. |
| Truck Temp save deferred to End LPN, not the LPN field's own submission | Matches the developer's explicit requirement that the record only be written once the operator has actually finished with that LPN, not at the start of it. |
| Split IBLPN photos stored locally only, no auto-sync off the device | Explicit developer decision (2026-07-10) - avoids building network/transfer infrastructure not actually requested; a manual `adb run-as` pull remains available for ad hoc review. |

## 4. Testing & Verification Methodology

Because this API's behavior is not documented publicly, every non-trivial claim across this engagement was verified one of several ways before being acted on:

1. **Live curl testing directly against a real customer Oracle instance**, using multiple real test accounts, including OAuth login, the initial handshake, control-key actions, entry submissions, and yes/no conflict resolution — run interactively, one call at a time in places, to closely mirror manual Postman testing and rule out automation-specific artifacts. Also used in `v3` to confirm the Truck Temp PATCH shape (405 on the query-filtered URL) and to inspect live shipment records (`cust_decimal_1`) before touching real data.
2. **The app's own on-device debug sheet**, which the customer captured and shared directly for the hardest bugs (facility code submission, back-button key, the "Invalid format" dismiss failure, and — in `v3` — the Split IBLPN blank-label/`tag` discovery) — comparing the exact request sent against the exact response received was what surfaced each root cause, faster and more reliably than remote reproduction.
3. **A written functional specification and step-by-step manual test plan supplied by the customer** for the TAB navigation feature (§2.7), executed against a real Receiving transaction (Dock=D22 through Ctrl-E End LPN) with real business data, cross-checked live in Postman by the customer in parallel before and after implementation.
4. **Direct on-device driving via ADB** (`v3` only) — building and installing each change on the connected Nokia C01 Plus (`flutter build apk --debug` + `flutter install --debug`), screenshotting via `adb exec-out screencap` to visually confirm UI changes (scan/calendar icons, the Split IBLPN camera button), and using `adb shell run-as <pkg>` to inspect and pull files from the app's private storage (confirming a captured photo actually persisted, and was a valid image, rather than assuming the file write succeeded).

Several plausible-sounding theories were proposed, tested live, and explicitly disproven and discarded during this process (see §2.3) rather than left as unverified assumptions — this is recorded in code comments and project memory so a future session doesn't re-litigate settled questions without new evidence. The same discipline applied in `v3`: an initial `_currentTransactionName`-based guess for the Split IBLPN camera button was tried, found not to work live, and replaced with the `tag`-based fix (§2.17) rather than assumed correct from reasoning alone.

## 5. Current Status

**`v2`** (all work through §2.11): all six original issues (§2.1-§2.6) are fixed, and the TAB navigation feature (§2.7) plus its four rollout fixes (§2.8-§2.11) are complete — built, installed, and verified end-to-end on the Nokia C01 Plus. `v2` has not been touched since the `v3` fork and remains in this state as the demonstrated POC.

**`v3`** (all work from §2.12 onward): the project split is complete and verified (both apps coexist on the test device); scan/calendar helpers are live on every entry field; Truck Temp is now correctly scoped to its one intended receiving transaction only, uses the correct `cust_decimal_1` field with facility/company-scoped lookups, auto-locks when a value already exists, and saves only on End LPN; the Split IBLPN photo capture feature is complete, with the camera button correctly positioned and a photo confirmed to save correctly to local storage end-to-end. All of the above verified via `flutter analyze` (clean except the same two pre-existing const-constructor infos) and live on-device testing, not just code review.

## 6. Known Limitations & Recommendations

1. **OAuth client secret is embedded in the app binary** (test-grade only). Before any production/distributed build: register the OAuth application as a Public client, or route token exchange through a backend service instead of calling Oracle's token endpoint directly from the device.
2. **No "click ahead and catch up" navigation.** Tapping directly on a not-yet-reached field (e.g. tapping LPN while Dock is still current) does not jump there — the operator must advance one field at a time via TAB/submit, matching the field order Oracle expects. This was considered but deliberately not implemented, since skipping over a field carrying an unconfirmed auto-suggested value needs the same "Required Field" handling already seen in §2.7, and doing that correctly for an arbitrary jump distance was judged out of scope for this session.
3. **The "another active session" conflict is understood to be routine/occasionally-flaky Oracle-side behavior on this specific environment**, not something further client-side changes are likely to eliminate entirely. If it's ever seen to fail even after 6 automatic attempts, that's the signal to check with a WMS administrator for genuinely stuck RF sessions on the affected account, rather than to widen the retry bound further.
4. **No automated test suite exists yet** for the RF flows; verification today relied on live manual/device testing. Given how much of this app's correctness depends on exact request/response shapes against a live, occasionally-flaky external system, an automated regression suite would have limited value without a way to mock Oracle's actual (and still only partially-understood) behavior — manual verification against the live instance remains the most reliable method for now.
5. **Split IBLPN photos are local-only, by design.** They stay in the app's private on-device storage with no automatic upload, sync, or export path. Reviewing a captured photo currently requires a manual pull (`adb shell run-as`, since app-private storage isn't reachable by a plain `adb pull` on a non-rooted device) — an explicit developer decision (2026-07-10), not a gap awaiting a fix.
6. **`docs/*.md` describe `v2`'s history verbatim from the fork point until this update** — a known, expected lag between forking `v3` and refreshing its documentation, now closed by this revision.
